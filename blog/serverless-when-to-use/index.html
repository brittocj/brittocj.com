1. Core Compute Models Compared

The three dominant compute models span a spectrum from full control to zero management:

ModelManagement ScopeScalingBillingTypical Use Cases
Virtual MachinesYou manage OS, patches, runtime, appsManual or autoscaling groupsPer-second or per-hourLong-running services, custom OS needs, full root access
Containers (ECS/EKS, ACI, Cloud Run)You manage container image, platform manages orchestrationScale to zero (managed) or manualPer-second while runningHTTP APIs, background workers, microservices with custom runtimes
Serverless (Lambda, Azure Functions, etc.)You manage only function code and configAutomatic, scales to zeroPer-invocation + resource-timeEvent handlers, webhooks, scheduled jobs, lightweight APIs
Key distinction: Serverless is a deployment and billing model, not a language or framework. The "functions" are just code units managed by a platform that provisions, scales, and bills automatically.

6. Cold Start Deep Dive

Cold start is the initialization delay when a serverless platform spins up a new instance of your function. It is the primary performance trade-off of serverless.

Contributing factors

FactorImpactMitigation
Runtime/languageJVM/.NET ~ 3-5s; Node.js/Python ~ 100-500msChoose a lighter runtime or use container images
Deployment package sizeLarger packages take longer to download/importMinimize dependencies, use layers, trim unused code
Memory allocationHigher memory = more CPU = faster initAllocate more memory if cost permits
Initialization codeHeavy setup (DB connections, SDK init) runs per cold startLazy-load dependencies, reuse connections in global scope
VPC attachmentENI provisioning adds 500ms-2s on AWSUse VPC-less design, or provisioned concurrency for VPC functions

Provisioned concurrency and warmed instances

ProviderFeatureUse case
AWS LambdaProvisioned ConcurrencyKeep functions pre-initialized for predictable latency
AWS LambdaSnapStart (Java only)Snapshots JVM after init, reducing cold starts to <1s
Azure FunctionsPremium planAlways-warmed instances, VNET connectivity
GCP Cloud FunctionsMin instancesKeep N instances always warm
OCI FunctionsPre-provisioned concurrencyKeep functions pre-initialized
Cloud RunMin instancesKeep N containers always ready
Cold start checklist: Measure p99 latency under load. Use provisioned concurrency/min instances for user-facing APIs. Optimize the global scope initialization. Avoid VPC unless necessary. Consider Cloud Run for HTTP workloads where cold starts matter.

Cost comparison example

A function with 512 MB memory invoked 100 times/second with 100 ms duration:

# Approximate monthly cost (720 hours)

# AWS Lambda:
# 100 * 3600 * 24 * 30 = ~2.6M invocations
# Duration cost = 2.6M * 0.1s * 0.5GB * $0.00001667/GB-s
# Total ~ $640/month

# GCP Cloud Run (min_instances=0):
# Same compute = 2.6M * 0.1s * 0.5 vCPU * $0.000024/vCPU-s
# Plus request cost = 2.6M * $0.0000024
# Total ~ $1,050/month (but no provision time cost)

# Fargate (always on):
# 0.05 vCPU * 730 hours * $0.04048/vCPU-hr
# Plus 1GB memory * 730 * $0.004445/GB-hr
# Total ~ $140/month (but always running)
Rule of thumb: Use serverless for bursty or low-trafficked workloads. For anything consistently above 10% of the month's free tier equivalent, calculate whether containers or reserved instances would be cheaper. The crossover point varies significantly by provider and workload profile.

9. Vendor Lock-in and Portability

FaaS platforms are deeply integrated with their cloud's event model, IAM, and managed services. Lock-in is real.

Abstract the platformWrap function calls behind an internal interface you control
Minimize cloud-specific eventsStandardize on HTTP/webhook triggers and message queues

10. Pitfalls and Best Practices

Serverless is powerful but easy to misuse. Here are the most common mistakes:

PitfallConsequenceSolution
Long initialization in global scopeEvery invocation pays the costMoved heavy init to lazy loading in the handler
No monitoring or loggingHard to debug in productionUse structured logs, correlate with trace IDs, set alerts
Ignoring concurrency limitsSilent throttling at scaleCheck default quotas, request increases, use provisioned concurrency
Putting everything in one functionHard to maintain, slow cold startsDecompose into small single-purpose functions
Not caching connectionsRepeated DB/API connection overheadReuse clients outside the handler
Ignoring dead-letter queuesFailed events are lostConfigure DLQ for async invocations
VPC attachment by defaultAdds seconds to cold startsOnly use VPC when accessing private resources

Best practices summary

CategoryPractice
DesignKeep functions single-purpose, stateless, and short
DependenciesMinimize packages, use layers, trim unused code
StateExternalize state to managed databases or caches
Error handlingReturn structured errors, use DLQs, retry with backoff
SecurityPrinciple of least privilege IAM roles per function
MonitoringLogs, metrics, traces, and alerts per function
TestingLocal unit tests, integration tests with real event payloads
DeploymentInfrastructure as code, blue/green or canary deployments
Final guidance: Serverless removes server management and scales to zero. It is excellent for event-driven workloads, APIs with variable traffic, and glue logic between services. It is a poor default for steady high-throughput systems or workloads with strict latency requirements at cold start. Always model your expected invocation count, duration, and memory before choosing serverless over containers.

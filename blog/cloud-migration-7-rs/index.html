Cloud Migration 7 R's Strategy: Complete Decision Framework

📅 February 12, 2022
⏱️ 15 min read

The 7 R's of cloud migration — Rehost, Replatform, Repurchase, Refactor, Retire, Retain, Relocate — provide a structured framework for evaluating every workload. This guide includes decision criteria, effort vs. value analysis, cost models, and real-world pattern matching to choose the right strategy for each application.

1. The 7 R's at a Glance

The 7 R's originated from Gartner's 5 R's (2011), expanded by AWS to 6 R's, and later to 7 with the addition of Relocate. Each represents a distinct migration pathway with different effort, cost, risk, and cloud-native benefit profiles.

RNameDescriptionEffortCloud-Native ValueTypical Timeline
1RehostMove VMs as-is to cloud (lift and shift)LowMinimalDays–Weeks
2ReplatformMinor optimizations during move (lift, tinker, shift)Low–MediumModerateWeeks–Months
3RepurchaseReplace with SaaS/managed service (drop and shop)MediumHighMonths
4RefactorRe-architect for cloud-native (re-architect)HighMaximumMonths–Years
5RelocateHypervisor-level move to cloud (VMware on AWS, etc.)LowMinimalDays–Weeks
6RetireDecommission unused/legacy systemsLowN/A (cost savings)Days
7RetainKeep on-prem for now (revisit later)NoneNoneOngoing
Key insight: Most enterprises use a mix. A typical portfolio: 40% Rehost, 25% Replatform, 15% Refactor, 10% Repurchase, 5% Retire, 5% Retain. Relocate is newer and applies mainly to VMware-heavy shops.

2. Decision Framework: How to Choose

Use this decision tree for each workload. Score each dimension 1–5, then map to the recommended R.

DimensionScore 1–2: Favor Rehost/RelocateScore 3: Favor ReplatformScore 4–5: Favor Refactor/Repurchase
Business criticalityLow (dev/test, internal tools)Medium (supporting systems)High (customer-facing, revenue-generating)
Technical debtLow (modern stack, well-documented)Medium (some legacy components)High (spaghetti code, outdated frameworks)
Scalability needsPredictable, stable loadSeasonal or moderate growthUnpredictable, elastic, bursty
Time to migrateUrgent (datacenter exit deadline)Flexible (6–12 months)Strategic (12+ months, phased)
Team cloud maturityLow (learning phase)Medium (some certifications)High (cloud-native experienced)
Compliance constraintsStrict (data residency, certifications)Moderate (some controls needed)Flexible (cloud-native controls OK)
License portabilityBYOL available, simpleComplex licensingSaaS replacement preferred
Dependency complexityFew, well-understoodModerate couplingTight coupling, chatty interfaces

Quick mapping

Total ScorePrimary StrategySecondary Option
8–16Rehost / RelocateReplatform
17–28ReplatformRehost or Refactor
29–40Refactor / RepurchaseReplatform
Exception: Retire and Retain are business decisions, not technical scores. If an app has zero users or is being replaced, Retire regardless of score. If compliance or latency mandates on-prem, Retain.

3. Rehost (Lift and Shift)

Move virtual machines to cloud with minimal changes. The VM image, OS, middleware, and application stay identical.

When to use

Good FitAvoid When
Datacenter exit deadline < 6 monthsApplication needs auto-scaling
Legacy apps with no source code / vendor support endedHigh licensing costs (Windows/SQL per-core)
Large portfolio, need quick winsArchitecture prevents horizontal scaling
Compliance requires identical environmentTechnical debt blocks future changes
Team lacks cloud skillsCost optimization is primary driver

Tools and patterns

ProviderMigration ToolTarget
AWSAWS Application Migration Service (MGN), VM Import/ExportEC2
AzureAzure Migrate, Azure Site RecoveryAzure VMs
GCPMigrate for Compute Engine, Transfer ApplianceCompute Engine
OCIOCI VM Migration, RavelloOCI Compute

Post-migration optimizations

  • Right-size instance types (often 30–50% over-provisioned on-prem)
  • Enable automated stop/start for non-prod
  • Move to reserved instances / savings plans after validation
  • Implement backup, monitoring, and patching via cloud services
Warning: Rehost alone often increases costs 20–40% vs. on-prem due to lack of right-sizing and cloud premium pricing. Plan Replatform follow-up within 6 months.

4. Replatform (Lift, Tinker, and Shift)

Make targeted optimizations during migration without changing the core architecture. Typical changes: OS upgrade, containerization, managed database, managed cache.

Common replatforming moves

From (On-Prem)To (Cloud)EffortBenefit
Self-managed MySQL/PostgreSQLRDS / Cloud SQL / Azure DatabaseMediumAutomated backups, patching, HA, read replicas
Self-managed Redis/MemcachedElastiCache / Memorystore / Azure CacheLowManaged scaling, multi-AZ
VM-based app serverContainer (ECS/Fargate, Cloud Run, ACA)MediumFaster deploy, density, portability
Windows Server 2012/2016Windows Server 2022 / Azure ArcLowSecurity updates, extended support
Physical load balancer (F5, Netscaler)ALB / NLB / Cloud Load BalancingMediumNative integration, auto-scaling
On-prem message queue (MQ, RabbitMQ)SQS/SNS / PubSub / Service BusMediumServerless, infinite scale
File server (SMB/NFS)EFS / Azure Files / FilestoreLowManaged, multi-AZ, scalable

Containerization as replatforming

# Typical replatforming path: VM → Container → Managed Service

# 1. Containerize existing app
FROM ubuntu:22.04
COPY app /app
RUN apt-get update && apt-get install -y openjdk-17-jre
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "/app/app.jar"]

# 2. Deploy to managed container service
# AWS: ECS Fargate or EKS
# GCP: Cloud Run (simplest) or GKE Autopilot
# Azure: Container Apps

# 3. Swap backing services to managed equivalents
# application.properties
spring.datasource.url=jdbc:postgresql://${RDS_ENDPOINT}:5432/db
spring.redis.host=${ELASTICACHE_ENDPOINT}
Rule of thumb: Replatform when you can achieve 80% of cloud-native benefits with 20% of refactor effort. Database and cache migration to managed services is the highest ROI replatforming move.

5. Repurchase (Drop and Shop)

Replace custom or legacy software with SaaS or managed cloud services. Trade customization for operational simplicity.

Common repurchase scenarios

Legacy SystemSaaS / Managed ReplacementMigration Complexity
Custom CRM / Siebel / On-prem SalesforceSalesforce, HubSpot, Dynamics 365High (data migration, process change)
Homegrown HRIS / PeopleSoft / Workday on-premWorkday, BambooHR, RipplingHigh
On-prem ERP (SAP ECC, Oracle EBS)SAP S/4HANA Cloud, Oracle Cloud ERPVery High
Custom BI / Cognos / BusinessObjectsLooker, Power BI, Tableau CloudMedium
Self-hosted GitLab / Jenkins / BambooGitHub Enterprise, GitLab SaaS, CircleCILow–Medium
On-prem monitoring (Nagios, SolarWinds)Datadog, New Relic, Grafana CloudLow
Custom identity / LDAP / ADFSOkta, Entra ID, Ping IdentityMedium
On-prem email (Exchange, Notes)Microsoft 365, Google WorkspaceLow

Data migration considerations

  • Schema mapping: Legacy schemas rarely map 1:1. Plan for data transformation layer.
  • Historical data: Migrate last 2–3 years hot; archive rest to cold storage (S3 Glacier, Azure Archive).
  • Delta sync: Use CDC (Change Data Capture) for near-zero downtime cutover.
  • Validation: Automated row-count, checksum, and business-rule validation post-migration.
Decision factor: Repurchase when TCO of SaaS (license + implementation + ongoing) < TCO of maintaining custom software over 3–5 years. Factor in opportunity cost of engineering time.

6. Refactor / Re-architect

Fundamentally redesign the application for cloud-native principles: microservices, serverless, event-driven, immutable infrastructure.

Refactoring patterns

PatternFromToWhen to Apply
Strangler FigMonolithMicroservicesIncremental migration, domain boundaries clear
Decompose by Business CapabilityMonolithDomain-driven servicesTeam autonomy needed, different scaling profiles
Event-Driven ArchitectureSync REST/RPCAsync events (Kafka, EventBridge)Loose coupling, audit trail, replay needed
Serverless FirstAlways-on servicesFunctions + managed servicesBursty traffic, event-driven, low ops overhead
CQRS / Event SourcingCRUD monolithSeparate read/write modelsComplex domain, audit requirements, temporal queries
Sidecar / Service MeshLibrary-based cross-cuttingInfrastructure-level (Istio, Linkerd)Polyglot, observability, security standardization

Refactor decision checklist

QuestionYes → RefactorNo → Replatform/Rehost
Will this app exist > 3 years?Invest in cloud-nativeMinimal changes
Does it need elastic scaling?Refactor for serverless/k8sFixed capacity OK
Are deployments painful/slow?Containerize + CI/CDCurrent process acceptable
Is tech stack end-of-life?Rewrite on modern stackSupported for years
Team ready to own services?Microservices viableKeep modular monolith
Start small: Pick one bounded context with clear domain boundaries, high change rate, and scalability needs. Prove the pattern, build team confidence, then expand.

7. Relocate (Hypervisor-Level Lift and Shift)

Move entire VMware clusters to cloud without converting VMs. The hypervisor runs in cloud (VMware Cloud on AWS, Azure VMware Solution, Google Cloud VMware Engine, Oracle Cloud VMware Solution).

When Relocate makes sense

ScenarioWhy Relocate
VMware-heavy estate (90%+ virtualized)Preserve operational tools, scripts, processes
Hardware refresh deadline < 6 monthsFastest exit, no app changes
Strict compliance (validated VMware configs)Maintain compliance posture
Team has deep VMware, no cloud skillsLeverage existing expertise
vSphere-specific features (DRS, HA, vMotion)Feature parity in cloud

Provider comparison

ProviderServiceKey Characteristics
AWSVMware Cloud on AWS (VMC)Native AWS integration, bare metal hosts, min 3 hosts
AzureAzure VMware Solution (AVS)Azure integration, min 3 hosts, Microsoft support
GCPGoogle Cloud VMware Engine (GCVE)Anthos integration, min 3 nodes
OCIOracle Cloud VMware SolutionOCI integration, flexible scaling, BYOL

Relocate → Replatform path

Relocate is rarely the end state. Typical evolution:

  1. Month 0–3: Relocate VMware cluster to cloud
  2. Month 3–6: Identify workloads for Replatform (databases → RDS, caches → ElastiCache)
  3. Month 6–12: Migrate replatformed workloads off VMware hosts
  4. Month 12+: Downsize VMware cluster, eventually decommission
Cost warning: Relocate has highest compute cost (dedicated bare metal). Plan to reduce VMware footprint within 12–18 months. Use as bridge, not destination.

8. Retire

Decommission applications that no longer deliver value. The fastest migration is the one you don't do.

Retirement criteria

SignalAction
Zero active users (check logs, APM)Immediate retire
Duplicate functionality (mergers, shadow IT)Consolidate, retire redundant
Replaced by SaaS (Repurchase done)Retire legacy after validation
Maintenance cost > business valueRetire or replace
Security vulnerabilities unpatchableUrgent retire
Compliance scope reductionRetire to reduce audit surface

Retirement checklist

  • Data retention policy: what to keep, for how long, where (archive to cold storage)
  • Dependency mapping: ensure no hidden consumers (API calls, batch jobs, reports)
  • Contract termination: vendor licenses, support agreements, hardware leases
  • DNS/redirect: graceful shutdown with redirect to replacement
  • Documentation: record retirement decision, data location, contacts for audit
Typical yield: 10–20% of portfolio qualifies for Retire. Average cost savings: 15–30% of infrastructure spend.

9. Retain (Revisit Later)

Keep on-premises for now with a defined revisit trigger. Not a "no" — a "not now."

Valid Retain reasons

ReasonRevisit Trigger
Data sovereignty / residency lawsCloud region opens in required jurisdiction
Ultra-low latency (< 1ms) to on-prem systemsEdge / local zone available
Mainframe / specialized hardware dependencyCloud mainframe service available (AWS Mainframe Modernization, etc.)
Massive data gravity (PB+ datasets)Direct Connect / Interconnect cost drops
Recent large investment (hardware refresh < 2 yrs)Depreciation complete
Regulatory certification in progressCertification complete

Retain governance

  • Document the reason, owner, and revisit date (max 12 months)
  • Apply cloud-like operations on-prem: IaC, monitoring, automation
  • Plan connectivity: Direct Connect, VPN, or Interconnect for hybrid
  • Include in cloud cost models (shadow IT prevention)

10. Migration Wave Planning

Don't migrate everything at once. Structure into waves by risk, complexity, and business value.

WaveFocusStrategy MixDurationGoal
Wave 0: FoundationLanding zone, networking, security, operationsN/A4–8 weeksReady to receive workloads
Wave 1: Quick WinsLow-risk, non-prod, dev/testRehost, Retire4–6 weeksValidate process, build confidence
Wave 2: Core MigrationProduction apps, grouped by domainRehost, Replatform8–16 weeksMigrate bulk of estate
Wave 3: OptimizationHigh-value apps needing cloud-nativeRefactor, Repurchase12+ weeksMaximize cloud value
Wave 4: Legacy/ComplexMainframes, specialized, retainedRelocate, RetainOngoingAddress remaining
Wave sizing: Limit Wave 1 to 5–10 apps. Wave 2 in batches of 10–20. Each wave ends with retrospective: update runbooks, adjust estimates, celebrate wins.

11. Cost Comparison and ROI

Migration strategy directly impacts 3-year TCO. This model assumes 100 VMs, mixed workloads.

StrategyMigration CostAnnual Run Rate (Yr 1)Annual Run Rate (Yr 3)3-Year TCOCloud-Native Value
Rehost only$200K$1.2M$1.0M (RI)$3.4MLow
Rehost + Replatform (DB, cache)$500K$900K$700K$2.8MMedium
Replatform + Selective Refactor$1.2M$800K$500K$2.6MHigh
Repurchase (SaaS for 30% apps)$800K$700K$600K$2.5MHigh
Relocate (VMware on AWS)$300K$1.5M$1.3M$4.1MLow

Hidden costs to model

  • Data egress: $0.02–0.09/GB between clouds/regions
  • Dual-run period: 2–4 weeks running both environments
  • Team training: $5–15K/person for certifications
  • Migration tooling: $10–50K for specialized tools
  • Validation/testing: 20–30% of migration effort
  • Rollback plan: Capacity reserved for fallback
ROI reality: Pure Rehost often has negative ROI Year 1. Break-even typically Year 2–3 after right-sizing, reserved instances, and replatforming. Refactor/Repurchase shows ROI faster for high-value apps.

Final guidance: The 7 R's are a portfolio tool, not a single-choice tool. Every application gets its own R. Revisit decisions annually — what was Retain last year may be Replatform this year as cloud services evolve. Document the rationale for each decision; it becomes your migration architecture decision record (ADR).

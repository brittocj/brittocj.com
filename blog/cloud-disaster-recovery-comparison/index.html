1. DR Strategy Fundamentals

Before comparing providers, understand the four canonical DR strategies. Each trades cost for recovery speed.

StrategyDescriptionRTORPOCostUse Case
Backup & RestorePeriodic backups to object storage; restore on demandHours–DaysHours–24h$Non-critical, dev/test, regulatory archive
Pilot LightCore infra (DB, networking) running; app scaled up on demandMinutes–HoursMinutes$$Critical apps, cost-conscious
Warm StandbyScaled-down full stack running; auto-scales on failoverMinutesSeconds–Minutes$$$Business-critical, faster recovery
Multi-Site / Active-ActiveFull capacity in multiple regions; traffic splitSecondsNear-zero$$$$Mission-critical, zero-downtime
Key insight: Most enterprises use a tiered approach: Tier 1 (revenue-generating) = Warm Standby or Multi-Site; Tier 2 (internal tools) = Pilot Light; Tier 3 (dev/test) = Backup & Restore.

AWS Elastic Disaster Recovery (DRS) Deep Dive

# DRS Architecture
Source Servers (on-prem / other cloud)
    │
    ▼
AWS Replication Agent (installed on source)
    │  Continuous block-level replication
    ▼
Staging Area Subnet (VPC in target region)
    │  Low-cost staging (EBS snapshots)
    ▼
Launch Templates + Conversion
    │  EC2 launch, driver injection, network config
    ▼
Recovery Instance (EC2 in target region)
    │  Point-in-time recovery (last 24h in 5-min increments)
    ▼
Failback to Source (optional)
    │  Replicate changes back

# Key Metrics
RPO: < 1 minute (continuous replication)
RTO: Minutes (typically 5-15 min for full stack)
Supported: Windows, Linux, VMware, Hyper-V, physical

AWS Backup: Centralized Policy Management

# AWS Backup Plan Example (Terraform)
resource "aws_backup_plan" "dr_plan" {
  name = "dr-backup-plan"
  
  rule {
    rule_name         = "daily-snapshots"
    schedule          = "cron(0 2 * * ? *)"  # 2 AM UTC daily
    target_vault_name = aws_backup_vault.dr_vault.name
    lifecycle {
      delete_after             = 30
      move_to_cold_storage_after = 7
    }
    copy_action {
      destination_vault_arn = aws_backup_vault.dr_vault_cross_region.arn
      lifecycle {
        delete_after = 90
      }
    }
  }
  
  rule {
    rule_name         = "hourly-continuous"
    schedule          = "cron(0 * * * ? *)"
    target_vault_name = aws_backup_vault.dr_vault.name
    lifecycle {
      delete_after = 7
    }
  }
}

resource "aws_backup_selection" "dr_selection" {
  iam_role_arn = aws_iam_role.backup_role.arn
  plan_id      = aws_backup_plan.dr_plan.id
  
  selection_tag {
    type  = "STRINGEQUALS"
    key   = "DR"
    value = "true"
  }
}

Aurora Global Database: Sub-Second RPO

# Aurora Global Database Setup
# Primary cluster in us-east-1
# Secondary cluster in us-west-2 (read-only, auto-replicated)

# Failover promotion (RTO < 1 min)
aws rds failover-global-cluster \
  --global-cluster-id my-global-cluster \
  --target-db-cluster-identifier my-secondary-cluster \
  --allow-data-loss  # or --no-allow-data-loss for controlled failover

# Key features:
# - Replication lag typically < 1 second
# - Up to 5 secondary regions
# - Secondary readable (offload reads)
# - Managed failover with Global Cluster API
AWS DR strength: Most integrated ecosystem. DRS for server replication, Aurora Global for database, S3 CRR for objects, Route 53 for DNS failover. Best for AWS-native workloads.

Azure Site Recovery (ASR) Deep Dive

# ASR Architecture
Source: Azure VMs, on-prem VMware/Hyper-V, physical servers
    │
    ▼
Mobility Service Agent (installed on source)
    │  Continuous replication
    ▼
Cache Storage Account (target region)
    │  Staging area
    ▼
Target Resources (pre-created or auto-created)
    │  Managed disks, NICs, NSGs
    ▼
Recovery Plan (orchestrated failover)
    │  Ordered groups, scripts, manual actions
    ▼
Failover / Test Failover / Planned Failover

# Key Metrics

RTO: 15-30 minutes (full stack recovery)
SLA: 99.9% for replication health

# Supported Sources
- Azure VMs (Windows/Linux)
- On-prem VMware vSphere 6.5+
- On-prem Hyper-V (2012 R2+)
- Physical servers (Windows/Linux)
- AWS EC2 (via mobility agent)

Azure SQL Geo-Replication

# Active Geo-Replication for Azure SQL Database
# Primary in East US, secondary in West US 2

# Configure via Azure CLI
az sql db replica create \
  --name mydb \
  --resource-group rg-primary \
  --server sql-primary \
  --partner-server sql-secondary \
  --partner-resource-group rg-secondary \
  --service-objective GP_Gen5_4

# Failover (initiated from secondary)
az sql db replica set-primary \
  --name mydb \
  --resource-group rg-secondary \
  --server sql-secondary

# Key features:
# - Up to 4 readable secondaries
# - RPO < 5 seconds (async commit)
# - Automatic failover groups (managed failover)
# - Supports Hyperscale tier

Cosmos DB: Native Multi-Region

# Cosmos DB Multi-Region (Active-Active)
# Configured at account level

az cosmosdb create \
  --name my-cosmos-account \
  --resource-group rg \
  --locations regionName=EastUS failoverPriority=0 isZoneRedundant=True \
              regionName=WestUS2 failoverPriority=1 isZoneRedundant=True \
              regionName=WestEurope failoverPriority=2

# Automatic failover (optional)
az cosmosdb update \
  --name my-cosmos-account \
  --enable-automatic-failover true

# Key features:
# - 99.999% availability (multi-region)
# - < 10ms latency (local reads/writes)
# - 5 consistency levels (Strong, Bounded Staleness, Session, Consistent Prefix, Eventual)
# - Automatic indexing, TTL, change feed
Azure DR strength: Best for hybrid scenarios (on-prem → Azure). ASR handles VMware/Hyper-V seamlessly. Strong for Windows/SQL Server workloads. Cosmos DB offers true multi-master.

GCP Backup and DR Service

# GCP Backup and DR (formerly Actifio)
# Agentless, application-consistent backups

# Supported workloads:
# - VMware VMs (on-prem / VMware Engine)
# - Compute Engine VMs
# - Cloud SQL (MySQL, PostgreSQL, SQL Server)
# - SAP HANA, Oracle, Microsoft SQL Server
# - Kubernetes (GKE) - via CSI snapshots
# - Filesystems (NFS, SMB)

# Key features:
# - Agentless (uses storage snapshots + VSS)
# - Application consistency (VSS, Oracle RMAN, SAP HANA Backint)
# - Deduplication + compression (typical 10:1)
# - RPO: 1 hour (snapshots), 5 min (streaming)
# - Instant mount for test/dev
# - Retention: hourly/daily/weekly/monthly/yearly policies

# Terraform example
resource "google_backup_dr_backup_plan" "dr_plan" {
  name        = "dr-backup-plan"
  location    = "us-central1"
  description = "Daily DR backups with 30-day retention"
  
  backup_rule {
    schedule = "0 2 * * *"  # Daily 2 AM
    retention = "720h"      # 30 days
  }
  
  backup_rule {
    schedule = "0 * * * *"  # Hourly
    retention = "168h"      # 7 days
  }
}

Spanner: True Global Database

# Spanner Multi-Region (Active-Active)
# Single database, globally distributed

gcloud spanner instances create my-instance \
  --config=regional-us-central1  # or multi-region config
  --nodes=3 \
  --description="Global DB"

# Multi-region config example:
# nam-us (North America), eur-us (Europe), asia-south1 (Asia)

# Key features:
# - 99.999% availability SLA
# - External consistency (stronger than strong)

GCP DR strength: Global load balancing (anycast) is best-in-class. Spanner/Firestore offer true multi-master. Managed Instance Groups provide self-healing compute. Best for cloud-native, globally distributed apps.

OCI Full Stack Disaster Recovery (FSDR)

# FSDR: Unique OCI capability - orchestrates entire stack
# No agents, no separate replication layer

# Protection Group = Logical grouping of resources
# DR Plan = Ordered steps with dependencies

# Supported Resource Types:
# - Compute: VMs, Bare Metal, Instance Pools
# - Database: Autonomous DB, Base DB, Exadata
# - Network: VCN, Subnets, Load Balancers, DRGs
# - Storage: Block Volumes, File Storage, Object Storage
# - Middleware: WebLogic, Kubernetes (OKE)
# - Custom: Any resource via CLI/SDK

# DR Plan Structure:
# Plan: "Production-Failover"
#   Group 1 (Network): VCN, Subnets, DRG, LPG
#   Group 2 (Storage): Block Volume replication start
#   Group 3 (Database): Data Guard switchover
#   Group 4 (Compute): Instance Pool scale-up, VM launch
#   Group 5 (Middleware): WebLogic domain start
#   Group 6 (Validation): Health checks, smoke tests

# Execution:
oci disaster-recovery dr-plan execute \
  --dr-plan-id ocid1.drplan.oc1.xxx \
  --dr-plan-execution-type FAILOVER

# Key Metrics:
# RTO: < 30 minutes (full stack, automated)
# RPO: Depends on replication (Block Volume: 15 min, Data Guard: < 1s)
# No agent on source (uses OCI APIs)
# Test failover without impacting production

Oracle Data Guard: Database DR Gold Standard

# Data Guard Configurations

# 1. Maximum Protection (Zero Data Loss)
# SYNC redo transport, standby must acknowledge
# Primary stalls if standby unavailable
# RPO = 0, highest impact on primary

# 2. Maximum Availability (Recommended)
# SYNC transport, but primary continues if standby lags
# Automatic failover with Fast-Start Failover
# RPO = 0 (when standby available)

# 3. Maximum Performance (Async)
# ASYNC transport, minimal primary impact
# RPO = seconds to minutes
# Best for geo-distributed

# Active Data Guard (Read-only standby)
# Offload reporting, backups to standby
# Real-time apply for near-zero lag

# Autonomous Data Guard (ADG)
# Fully managed for Autonomous Database
# Automatic failover, patching, backups
# RPO < 1s, RTO < 2 min

GoldenGate: Heterogeneous Replication

# GoldenGate 23c (Microservices Architecture)
# Real-time data mesh

# Sources: Oracle, MySQL, PostgreSQL, SQL Server, MongoDB, Kafka, BigQuery
# Targets: Same + ADW, Snowflake, Redshift, ADLS

# Deployment:
oci goldengate deployment create \
  --display-name gg-deployment \
  --subnet-id ocid1.subnet.oc1.xxx \
  --license-model BRING_YOUR_OWN_LICENSE

# Pipeline: Capture → Transform → Replicate
# - Schema evolution (DDL replication)
# - Conflict detection/resolution
# - Data filtering, masking, enrichment
# - Exactly-once delivery

# Use cases:
# - Multi-cloud DR (Oracle → PostgreSQL on Azure)
# - Real-time analytics (CDC to data lake)
# - Zero-downtime migration
# - Active-active across clouds
OCI DR strength: Full Stack DR automates entire stack failover without agents. Data Guard is the most mature database replication. GoldenGate enables heterogeneous/multi-cloud DR. Best for Oracle database workloads and hybrid enterprises.

Decision Tree


START: What is your primary database?
├── Oracle → OCI (Data Guard best-in-class)
├── SQL Server / Windows-heavy → Azure (ASR + SQL Geo-Replication)
├── Cloud-native / Global scale → GCP (Spanner + Global LB)
├── AWS-native / Broadest services → AWS (DRS + Aurora Global)
└── Heterogeneous / Multi-cloud → OCI (GoldenGate) or Multi-provider

Then: What RTO/RPO do you need?
├── RTO hours, RPO 24h → Backup & Restore (any provider)
├── RTO 30-60 min, RPO minutes → Pilot Light
├── RTO 15-30 min, RPO < 5 min → Warm Standby
└── RTO seconds, RPO near-zero → Multi-Site (Active-Active)

Then: Hybrid or Cloud-only?
├── On-prem → Cloud → Azure ASR, AWS DRS, GCP VMware Engine, OCI FSDR
└── Cloud → Cloud → Native replication services

Finally: Budget constraint?
├── Lowest cost → OCI Pilot Light, GCP Backup & DR
├── Balanced → Azure Warm Standby, AWS Pilot Light
└── No constraint → Multi-Site on GCP (Spanner) or AWS (DynamoDB Global)
